# Translations (desktop UI)

Scope: the desktop app (`relay-ui` and `relay-desktop`: window text, tooltips, tray menu, notifications). The CLI is not translated. Phase 1 (this) is the plumbing and the complete English catalog; the other eight languages are empty stubs waiting for translators.

## Languages

English `en` (default and fallback, always first in the picker), then by English name: German `de`, Hindi `hi`, Japanese `ja`, Korean `ko`, Portuguese (Brazil) `pt-BR`, Russian `ru`, Spanish `es`, Simplified Chinese `zh-CN`. The picker in Settings shows each by its own name (Deutsch, हिन्दी, 日本語, 한국어, Português (Brasil), Русский, Español, 简体中文). `relay_ui::i18n::Language::ALL` is the single list.

## Layout

```
localizations/<lang>/<section>.ftl
```

`localizations/` is at the repository root. Every language folder has the same ten section files (`common calls peers audio channels settings messages tray notifications errors`), one per area of the app, each well under 500 lines. A section file is Project Fluent (`.ftl`). All sections of a language are merged into one Fluent bundle at start, so an id is defined in exactly one section (the checks enforce it). Files are embedded with `include_str!` (`crates/relay-ui/src/i18n/catalog.rs`); there is no runtime file access.

## Adding or changing a string

1. Pick a stable semantic id (`settings-hotkey-title`, not the English words) and add it to the right section of `localizations/en/`.
2. In code use `relay_ui::tr!`: `tr!("id")` returns `&'static str` (cached, no allocation per frame); `tr!("id", count = n, name = who)` returns a `String`. The id must be a string literal.
3. Plurals and grammar belong in the message, not in code: use a Fluent selector (`{ $count -> [one] ... *[other] ... }`). Do not build sentences from pieces; pass whole values as variables.
4. Run `cargo test -p relay-ui --test i18n_keys --test i18n_catalogs`.

## Adding or translating a language

Fill the section files of `localizations/<lang>/` (they start as header-only stubs). Translate the value, keep the id and every `$variable` name. A message you leave out falls back to English, per message. Adding a new language also needs a `Language` variant, its folder with all section files, and the `include_str!` lines (the compiler points at each).

**The check translators run:**

```
cargo test -p relay-ui --test i18n_catalogs
```

It fails when a language has a syntax error, an id English lacks, an id in a different section than English, an id defined in two sections, `$variables` that differ from English's, or a folder whose section files differ from English's. `cargo test -p relay-ui --test i18n_keys` checks the code side (every id used exists in English, none unused).

## What is translated and what is not

Translated: every string the UI composes, including tooltips and hover text, status and error wording the UI builds, local validation messages, the tray menu and tooltip, notification title and unknown-caller text, native dialog titles.

Kept as received or as is:

- Text that arrives from the daemon or engine over the API (problem messages, recovery actions, warnings, failure reasons, role words such as `owner`) is shown as received. The UI words its own explanation of known problem codes (`problem-*`, `delivery-*`) and translates that.
- Protocol values, file names, device and channel names, peer display names, message text, fingerprints and the product name `Relay`.
- Sizes (`1.5 MiB`), percentages, `dBFS`, `ms` and clock times keep one format in every language (units are IEC or international symbols, decimals use a dot). Timestamps use the system time zone and `jiff` formatting, not the language. Counts are passed to Fluent, which applies each language's plural rules.
- Log and tracing output, and internal invariants that are never shown.

## Language setting

Stored in `desktop.toml` (per-user config directory) as `language = "de"`, beside `notify_incoming`. Absent or unknown means the system language: `sys-locale` gives the preferred locales, `i18n::locale::match_locale` maps each (`pt_BR.UTF-8` to `pt-BR`, `zh_Hans_CN` to `zh-CN`, any `pt` to `pt-BR`, `zh-TW`/`zh-Hant` to no match, unknown to the next locale) and English is the last resort. Choosing a language in Settings applies on the next frame with no restart: the catalogs switch, the fonts are reinstalled (order depends on language, see `docs/ui.md`) and the tray menu and tooltip are relabelled within a second. The picker has no "system" entry (English must stay first); once a language is picked it is explicit.

## Known limits

- Hindi is experimental: egui does no complex text shaping, so Devanagari conjuncts and vowel-sign reordering are not formed. The picker labels it "(experimental)".
- Window and dialog titles derive egui ids from text, so a language change closes an open dialog or collapsible state.
- A translated message that reaches the user from an earlier moment (a stored notice, an error banner) stays in the language it was created in.

## Review gate

Translations are machine-written and need review by a native speaker before release. This is a release gate (`docs/gates.md`, cross-cutting gates): a language ships only when its section files were reviewed by a native speaker and `cargo test -p relay-ui --test i18n_catalogs` passes. An unreviewed language must not appear in the picker of a release build.
