# Local control API

Living notes for `crates/relay-api`. The contract is `crates/relay-api/proto/relay/v1/engine.proto`; Rust stubs are generated by `build.rs` (vendored `protoc`, no system install needed) into `relay_api::pb`. Generated types are wire types only; the engine crate converts them to validated domain types.

## Transports

| Platform | Endpoint | Status |
|---|---|---|
| Unix | UDS `$XDG_RUNTIME_DIR/relay/engine.sock`, else `<tmp>/relay-<uid>/engine.sock` | implemented, tested |
| Any | Loopback TCP + bearer token profile file (fallback) | implemented, tested |
| Windows | Named pipe with current-user DACL | **unmet spike**, not implemented |

### Unix socket rules
- Directory created `0700`; an existing directory must be a real directory (no symlink) owned by us, and is tightened to `0700` if loose.
- Socket is `0600`. Every accepted connection is checked with `peer_cred()`; other uids are dropped and logged.
- Stale detection: an existing path must be a socket we own; if connecting gets `ECONNREFUSED` it is removed and rebound, if it connects the bind fails with `AlreadyRunning`. A non-socket file is never touched. PID files are not used.
- `current_uid` and `prepare_runtime_dir` need a tokio runtime context.

### Loopback TCP profile
`bind_loopback(path)` binds `127.0.0.1:0`, writes `addr=` and `token=` (64 hex chars from two v4 UUIDs) to a `0600` file. Clients refuse a profile that is group/world accessible, non-loopback, or has a short token. Every RPC needs `authorization: Bearer <token>` (constant-time compare). No CORS or browser access. Loopback is not authentication against a same-user hostile process. On Windows the file mode is not enforced (ACL hardening unmet).

## Client context and middleware
`GetInfo` and `RegisterClient` are the only unauthenticated-by-context methods. All others must carry metadata `relay-client-id` (32 hex chars) and may carry `relay-incarnation`. `GuardLayer` validates these through a `ClientValidator` (`ClientRegistry` is a bounded reference implementation, 32 clients) before the handler runs: unknown id is `UNAUTHENTICATED`, stale incarnation is `FAILED_PRECONDITION`, malformed is `INVALID_ARGUMENT`. The engine must still check that the body's `ClientContext` equals the header. A client id is an identifier, not authentication.

Limits (`ApiLimits::DEFAULT`): messages of 1 MiB plus 64 KiB of envelope (tonic encode/decode caps plus an early `content-length` reject, `RESOURCE_EXHAUSTED`/`OUT_OF_RANGE`), 64 requests in flight, 96 open streams, 256-event subscriber queues. Streaming handlers must call `StreamLimiter::acquire()` and keep the guard in their stream task.

## Operations
Each mutation carries a 16-byte `operation_id`. Same id + identical request returns the stored outcome; same id + different request is `ALREADY_EXISTS` (`OPERATION_ID_REUSED`). Retention (4,096 per client, 10 minutes) is the engine's job. `RelayClient::wait_operation` polls `GetOperation` until the state leaves `ACCEPTED`.

## State watching
`WatchState` without `after_revision` begins with an atomic snapshot. `StateTracker` rejects non-increasing revisions, revision gaps (unfiltered watches only; filters may legitimately skip), and incarnation changes. `ResyncRequired` means: open a fresh watch. `snapshot_and_watch` resumes at `snapshot.revision` and relies on engine replay; a missed window yields `Resync`. `StateWatch::into_bounded(n)` moves reading to a task and ends with `SubscriptionOverflow` instead of buffering when the consumer lags.

## Channels, avatars, connection info
- Channel RPCs (`CreateChannel`, `JoinChannel`, `LeaveChannel`, `ListChannels`, `CreateInvite`, `RevokeChannelMember`) follow `docs/channels.md`. `Snapshot.channels`, `Peer.shared_channel_ids`, `Settings.inbound_policy` and `Settings.advert_mode` expose state; `SetPrivacy` changes the last two.
- Failed channel operations carry stable `Problem.code`s: `CHANNEL_DENIED` (uniform for unknown channel, wrong secret, bad or spent invite), `CHANNEL_LOCKED_OUT`, `CHANNEL_LIMIT`, `CHANNEL_NAME_INVALID`.
- Passwords and invite secrets live only in request bodies (and the `CreateInviteResponse`). The generated `Debug` is disabled for those messages and replaced by redacting impls; the guard logs method paths only (`SENSITIVE_METHODS` lists the affected RPCs). The engine must not put them in events, snapshots, operation results or logs.
- `GetAvatar(hash)` returns a canonical PNG up to `AVATAR_MAX_BYTES` (1 MiB; the default message limit is that plus 64 KiB of envelope); unknown hash is `NOT_FOUND`. `RelayClient::get_avatar` rejects larger answers.
- `GetConnectionInfo` returns eligible LAN addresses, listen port, local fingerprint and an opaque `connection_string` filled by the engine. `StartCallRequest.target` also accepts `manual_connection_string`.

## Client sketch
```rust
let mut c = RelayClient::connect(&Endpoint::Unix(path)).await?;
c.register("relay-cli", env!("CARGO_PKG_VERSION"), &["observe"]).await?;
let (snapshot, mut watch) = c.snapshot_and_watch().await?;
```

## Engine integration
Implement `pb::engine_server::Engine`, own a `ClientRegistry` (or a custom `ClientValidator`), bind `UdsListener`, and call `serve_unix` (or `serve_tcp`). `engine_server()` applies message limits when wiring by hand.

## Open gates
Windows named pipe; Windows ACL on the TCP profile; per-client operation cache and rate limits; telemetry and `InputControl` stream semantics (engine-side); cross-version compatibility matrix tests.
